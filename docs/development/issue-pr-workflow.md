# 1サブIssueから1 PRまで

1. 作業前に `AGENTS.md`、現行正本、最新の実装監査、対象Issueの受入条件を読む。担当・レビュー担当と作業範囲を決め、未割当のままならそのまま記録する。Designまたは人間レビュー待ちの案は、採用範囲と正本の合意まで実装対象にしない。
2. 対象リポジトリ・ベースSHA、依存Issueと既存PRを確認する。依存が未マージなら、その事実を記録し、必要に応じて依存PRをベースに積む。ベースのブランチに実装があることをmainへの統合済みと扱わない。並行作業は別ブランチ・別worktreeまたは別cloneとし、共有型・認証・ルート・ロックファイルの衝突を調整する。
3. サブIssueごとに実装と関連テストを用意する。認証、承認版の不変性、進行中の版固定、停止優先など影響する既存の受入条件も確認し、外部サービスの実動作を試せなければ未検証と記録する。仕様変更が必要な場合は同じPRで正本を更新し、人間のレビューに回す。
4. 対象SHAを固定し、必要なテスト・型検査・ビルドと差分検査を行う。実行環境と結果をPRに書く。別ブランチの統合を含む場合は両側の意図と検証範囲を記録し、依存先が更新・マージされた後に影響する検証をやり直す。独立してレビューできない積み重ねはドラフトにして依存先と順序を明記する。
5. サブIssueごとのブランチをpushし、PRテンプレートを埋めて作成する。実装担当・レビュー担当、テスト対象SHA、未実施と未解決事項を明記する。レビュアーが決まったら、担当者が適切な権限と通知先を確認してレビューを依頼する。未決なら未割当のままにし、レビュー済みとは扱わない。自動マージはしない。

必要な権限は、対象リポジトリの読み取り、ブランチのpush、PR作成、必要に応じたレビュアー指定。外部クラウドへの接続・デプロイ権限は実装PRの作成とは別。認証情報は記録やPRへ貼らない。

## 実施例と残る確認

2026-11-09、Issue #78について、担当Codexが #139 をベースに `4ba08a7` を作成し、[PR #140](https://github.com/Genk-AI/df-2026-t055/pull/140) をドラフトで作成した。全288テスト、ビルド、型検査を実施し、その後の関連修正は対象テストを追加実行した。#139以前が未マージであること、実利用者・実環境での確認が未実施であることをPRに記載した。レビュー担当は未割当で、レビュー依頼・独立レビューはまだ行っていない。このためIssue #37のレビュー依頼までの受入条件は未完了。
